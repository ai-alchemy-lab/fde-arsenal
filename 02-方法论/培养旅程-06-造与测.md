# 培养旅程 · 06 造与测：一个人带一支 agent 军团

> **这一站谁是主角**：FDE 本人，加上他的 agent 军团。
> **这一站要赢什么**：真实用户第一次上手操作。是登录记录，不是演示视频。
> **典型耗时**：10 到 14 天。

---

## 一、先定形状：个体制，不搞配对

Palantir 前线的标准编制是两个人：**FDSE**（管造）和 **Deployment Strategist**（管推）。一个对「系统能不能跑、跑得稳不稳」负责，一个对「有没有人用、价值算不算得清、组织里推不推得动」负责。这套配对经过了二十年验证，本库 [Echo-Delta 配对](echo-delta-配对.md) 有完整拆解。

**但我们不抄它**。内部 FDE 走个体制——一个人，带一支 agent 军团。

理由有三条：

**第一，配对在企业内部是一种奢侈品**。Palantir 派两个人进场，是因为客户在付钱。你在自己公司里做第一仗，能把一个人的六成时间抠出来已经是第 2 站打过一场硬仗的结果。要两个人，这个项目大概率立不起来。

**第二，配对解决的问题，内部人本来就没有**。DS 这个角色存在的核心理由是**外部人不了解客户组织**——他要花大量时间做组织导航、找拍板人、读会议室里的权力结构。而内部 FDE 在第 1 站就是按「组织导航」这一项挑出来的，他本来就认识这些人。**把外部人的分工方案照搬到内部，等于为一个你没有的问题付费**。

**第三，也是最重要的一条：2026 年配对里那个「推」的角色，一半的执行工作可以交给 agent**。调研、材料准备、进度跟踪、日报周报、访谈转写与归纳——这些原来占据 DS 大量时间的活，现在是 agent 的活。人留下的是判断和露面。

所以这一站的正确心智不是「我一个人要干两个人的活」，而是：

> **你是这支小队的指挥官。agent 是兵，你是唯一那个负责任的人**。

**一个必须说清楚的例外**：个体制不等于孤军。第 4 站里那个「被动了奶酪的人」、第 2 站里那次「负责人亲自出面」——**涉及组织政治的硬仗，仍然需要你的负责人露面**。个体制说的是执行编制，不是政治后盾。

## 二、agent 军团编制：四个岗位

不要用一个通用助手干所有事。**分成四个有明确职责、明确输入输出、明确交接物的 agent**，理由和企业里分工的理由一样：职责混在一起，质量无法归因。

| agent | 它干什么 | 你给它什么 | 它交给你什么 | 你在这里守什么判断 |
|---|---|---|---|---|
| **调研 agent** | 外部检索、同行做法、技术选型、失败案例 | 具体问题 + 已知约束 | 一页简报 + 三个可选方案 + 每个方案的已知坑 | 选哪条路，以及哪些「行业最佳实践」在我们这儿不成立 |
| **数据 agent** | 剖面统计、清洗、字段对齐、口径核对 | 数据切片 + 第 4 站的数据地图 | 字段质量报告 + 异常清单 + 可用数据集 | 哪个异常是脏数据，哪个异常是真实业务 |
| **代码 agent** | 写、改、测、部署 | 一次一个明确的小目标 | 能跑的东西 + 它自己的自测结果 | 范围切在哪、什么时候停手说「这版就这样」 |
| **推进 agent** | 日报、进度跟踪、会议纪要、汇报材料、待办跟催 | 每天的原始记录 | 一句话通报 / 周报 / 汇报草稿 | 哪句话能对外说，哪句话不能 |

### 每个岗位的任务指令怎么下（可直接抄）

**调研 agent**——最容易被用废的一个，因为大多数人只会问「XX 怎么做」。正确的下法是给约束：

```
背景：制造企业客服工单自动分类，12 个类别，中文，日均 2000 条，
      历史数据 6 个月，标注质量一般（人工历史标签错误率约 15%）。
约束：不能用外部 API（数据不出内网），可用本地开源模型，
      我一个人做，两周内要有能给真人用的东西。
任务：给我三条技术路线，每条包含：
  1) 大致做法（不超过 5 行）
  2) 两周内做出来的可能性（高/中/低）和理由
  3) 已知的失败模式——具体是什么情况下这条路会崩
  4) 需要我提前确认的一件事
不要给我通用的最佳实践列表。不要推荐需要标注 10 万条数据的方案。
```

**注意最后两句**。不写这两句，你会拿到一份维基百科式的技术综述。**约束条件写得越具体，调研 agent 的价值越高**——这一点和你带一个新人一模一样。

**数据 agent**——它的价值在于发现你想不到要问的事：

```
数据：附件是退货单主表 3 万行、明细表 12 万行的切片。
先做常规剖面：每个字段的空值率、取值分布、极值、时间分布。
然后重点回答这五个问题：
  1) 哪些字段在某个时间点前后行为明显不同？（可能有口径变更）
  2) 哪些字段名义上是枚举，实际出现了未文档化的取值？
  3) 主表和明细表关联，有多少条关联不上？关联不上的有什么共同特征？
  4) 有没有明显是"被挪作他用"的字段？（比如备注栏里塞了结构化信息）
  5) 如果我要按"华东区 + 2026 年 + 退货类"取子集，实际能取到多少条？
最后列出：你认为我应该去问业务方的三个问题。
```

**最后那一句是这个指令里最值钱的一行**。它把 agent 从「回答我问的」变成「告诉我该问什么」。

**代码 agent**——核心纪律是**一次一个小目标，且每个目标都要能验证**：

```
目标：把 data/eval_v1.jsonl 里的 300 条邮件跑一遍分类，
      输出 pred.jsonl，字段 id / pred_type / pred_urgency / confidence。
约束：用 prompts/classify_v3.txt 里的提示词，不要改它。
      失败的条目不要跳过，写进 failed.jsonl 并记录原因。
完成后：跑 scripts/score.py，把分层准确率贴给我。
```

**不要下「帮我做一个客服分类系统」这种指令**。不是因为它做不了，是因为它做出来的东西你没法判断对不对——**你失去了判断点，就等于把这一仗交出去了**。

**推进 agent**——最被低估的一个：

```
输入：今天的工作记录（见下）。
产出三样：
1) 给业务群的一句话通报，格式："今天根据 X 的反馈改了 Y。"
   要具体到人名和改动内容，不要写"优化了系统性能"。
2) 明天要办的三件事，按优先级。
3) 需要别人配合的事项清单，每条写清：找谁、要什么、什么时候要。
纪律：通报里不出现"赋能""闭环""智能化"这类词。
      不确定的进展不要写成已完成。
```

### 你在这个编制里的位置

一天大概长这样：

| 时段 | 你在干什么 | agent 在干什么 |
|---|---|---|
| 早 30 分钟 | 看昨天的跑批结果和用户反馈，定今天的一个目标 | 已经跑完昨晚的批处理，日报在等你 |
| 上午 | **下指令、看中间结果、做判断** | 数据 + 代码在干活 |
| 中午 | **去现场**。和用户吃个饭，看他们用 | 后台继续跑 |
| 下午 | **给用户看半成品，挨骂，当场记** | 推进 agent 在整理上午的记录 |
| 晚 30 分钟 | 决定明天改什么，发一句话通报 | 跑今晚的评估集 |

**注意「中午去现场」和「下午给用户看」这两格是不能被 agent 替代的，也是最容易被跳过的**。一个人带 agent 军团最大的风险不是做不出东西，是**做得太顺，顺到你一整天都没离开屏幕**。

## 三、三条 MVD 军规

MVD（最小可行部署）的裁判和 POC、MVP 都不一样：

| | POC | MVP | MVD |
|---|---|---|---|
| 目的 | 证明技术可行 | 验证市场需求 | **证明业务价值** |
| 裁判 | 技术评审 | 早期用户 | **业务现场** |
| 数据 | 样例、脱敏假数据 | 早期用户自带 | **生产数据切片** |
| 及格线 | 能跑通 | 有人愿意用 | **业务指标动了，一线在用** |

**POC 的终点是一次演示，MVD 的终点是一个还在跑的系统。演示完鼓掌散会的，都不算**。

### 军规一：只用真实数据，没有例外

第一天就接真实数据切片（第 3 站已经拿到授权，第 4 站已经拿到手）。理由很硬：**企业数据的真实难度占了工作量的一大半**——外星表名、四种日期格式、同一种缺陷在三个分厂三套叫法、名义上叫「缺陷等级」实际被挪用成备注栏的字段。用样例数据，等于把最难的部分留到最后。

本库 [败 · POC 陷阱](../04-案例库/败-poc陷阱.md) 就是这条军规的反面标本：厂商用 300 份格式干净的样例报告两周做出 POC，演示惊艳，签约走绿色通道；真实数据一接进来全变了，第 12 周只跑通一个分厂的一部分，第 20 周例会没有业务方参加，系统停在会议室里，**没有人宣布项目失败，它只是安静地从所有人的日程里消失了**。

### 军规二：缩小范围，不缩小价值

可以只做一个部门、一类单据、一条产线，但**必须打通从数据进到业务结果出的完整链路**。

判断标准只有一句：**做完之后，公司里有没有一个具体的人，他每天的某个动作因此变了**。

### 军规三：锁死期限

期限是纪律工具。它逼你砍需求、逼别人配合、逼双方在「完美」和「能用」之间选能用。

这一条借自 Basecamp《Shape Up》的 **fixed time, variable scope**（固定时间、可变范围）：先定「愿意花多少时间」，再把方案锤进这个时间里，而不是先估工期。以及它的**断路器**规则：周期结束时没做完的东西不自动滚入下个周期。

到期那天只有三个词：**继续、调整、停止**。

## 四、两周节拍（逐日）

节拍参照 Palantir 驻场的真实节奏：**上午写的东西下午就进用户迭代会**，一周跑 4 到 5 个完整循环。（Palantir 部署策略师的公开日程实录里，10:15 在做数据管道，13:30 就开客户迭代会展示上午刚做的进展。见 [01-原典/07](../01-原典/07-Palantir-DeploymentStrategist的一天.md)。）

| 天 | 干什么 | 当天的硬约束 |
|---|---|---|
| **D0** | 数据切片实际到手、Eval 定稿、范围切割卡填完 | **数据没到手不许开工** |
| **D1** | 目标对齐会（业务负责人在场，把成功定成一个数字）；下午开始接数据 | 会议纪要当天发出，含那个数字 |
| **D2–D3** | 打通第一条最窄的端到端链路。丑没关系 | **D3 结束必须端到端跑通一条**，哪怕只有 10 条数据 |
| **D4** | **第一次给真实用户看半成品** | 这一天不许推迟。半成品见人是这个方法的核心纪律 |
| **D5** | 按反馈改；和业务负责人对一次「范围还砍不砍」 | 周复盘，评估集跑一次 |
| **D6–D8** | 加固：权限、异常处理、边界情况。把 D4 挨的骂逐条消掉 | 每天下午继续给人看 |
| **D9** | 真实用户试运行一整天，你在旁边看着，记录每一次卡壳 | **你必须在场，不许远程** |
| **D10** | 验收演示。**由用户自己操作**，不是你演示 | 当场决定下一步 |

### 为什么 D4 不能推迟

D4 是这份节拍表里唯一一个「反直觉」的日子。到了 D4，东西一定很丑，你一定会想「再改两天再给人看」。

**不许**。三个理由：

1. **早暴露的问题便宜**。D4 发现方向错了，你还有 6 天；D9 发现方向错了，这一仗结束了。
2. **一起改过五轮的用户会把你当自己人**。迭代密度就是信任积累的速度。这不是软性收益，它直接决定第 7 站的采纳。
3. **你需要他的抱怨，不需要他的赞美**。一个打磨过的成品会得到「挺好的」，一个半成品会得到「这个字太小了我看不清」——**后者才是有用的信息**。

### D9 那一天你在旁边看什么

带一个本子，记三样，**只记不说**（这一天你张嘴帮他，就浪费了这一天）：

- **每一次他停顿超过 3 秒的地方**——那是他不知道下一步该干什么；
- **每一次他去问别人 / 打开另一个窗口**——那是你的系统没覆盖到的信息需求；
- **每一次他绕过系统直接用老办法**——那是这个系统在他心里的真实位置。

## 五、范围切在哪一刀

这是这一站最重要的判断，用 [MVD 范围切割卡](../03-模板库/mvd范围切割卡.md)。四问，**必须都答「是」才能砍**：

1. 砍掉这块之后，**数据还是真实的**吗？
2. 砍掉这块之后，**还有一个具体的人的具体动作会因此改变**吗？
3. 砍掉这块之后，**第 3 站定的那个指标还测得出来**吗？
4. 砍掉这块之后，**用户还能在他原来干活的地方拿到结果**吗？

### 好的切法 vs 坏的切法（正反例）

| 好的切法（缩覆盖面） | 坏的切法（断链路） |
|---|---|
| 只做华东区的退货单 | 先不接真实数据，用导出的样表 |
| 只做 12 类工单里最高频的 3 类 | 先做分类，写回下一期再打通 |
| 只给 5 个人用，不全员开放 | 先做个查询界面，不改任何人的动作 |
| 只做文字工单，语音的下一期 | 界面先糊弄一下，能看就行 |

右边这三条——「**先不接真实数据**」「下一期再打通写回」「界面能看就行」——是中国企业 AI 项目 POC 化的三大典型死法。看到自己在说这三句话中的任何一句，停下来。

「先做查询不做写回」这一条要单独说。Palantir 的 Ontology 里有一个叫 **Action Type** 的原语，官方定义是「用户可以一次性执行的、对对象/属性值/关系的一组变更的模式定义」——**它的存在意味着 Palantir 把「写回」当成一等公民**。一个只能查询、不能改变世界状态的系统是不完整的。（出处：Palantir 官方文档 <https://www.palantir.com/docs/foundry/ontology/core-concepts>。）

我们没有 Palantir 的产品架构来强制这件事，只能用检查表强制：**只读的系统不改变任何人的动作，也就不产生任何采纳**。

### 顶住「能不能顺便加个 X」

这句话一定会来，而且大概率来自老板或者部门负责人，拒绝的社交成本极高。三步走：

1. **当面记录，让对方看到你在记**。掏出本子或者当场在群里发一条「记一下：XX 提的 YY 需求」。
2. **承认价值**：「这个确实有用，而且比我现在做的这块可能更值钱。」
3. **挂到第二仗**：「我把它放进第二仗清单，第 X 天汇报的时候我们一起看要不要接着做。现在动它，说好的那个数字我第 X 天交不出来。」

**零例外原则**：第一仗期间，**一个需求都不加**。破例一次，后面就守不住了。

## 六、进场姿势：读旧、写新、顺人

- **读旧**：不动任何现有生产系统，只从里面读数据。任何「先把你们那个系统换掉」的方案都是找死，而且第 2 站的授权书第四条也不允许。
- **写新**：新流程、新界面做成增量，架在老系统旁边，**出问题随时能退回原来的干法**。这个退路的存在决定了推进速度——人肯试新东西，是因为知道试坏了能退回去。
- **顺人**：顺着一线现有的工作习惯设计交互。他们在 Excel 和微信里干活，结果就送回 Excel 和微信；他们在车间戴手套，就上语音。**系统可以新，入口必须旧**。

为了显得先进而逼一线学一个新门户，是第 7 站死亡的头号原因。这一条第 7 站还会展开。

## 七、一个「造」的样板：Airbus 那一仗

2015 年，Nabeel Qureshi 入职 Palantir 后被派到法国图卢兹，接手他职业生涯第一个大项目。题目由空客最高层亲自定：**把 A350 的月产量从 4 架爬到 8 架，再往 16 架走**。

注意这个题目的措辞。空客没有说「帮我们升级数据基础设施」，也没有说「建一个数据平台」。CEO 关心的只有一件事：**每个月能下线几架飞机**。

Nabeel 搬到图卢兹住了一年半，每周四天泡在总装厂里。因为 A350 的部件在英、西、德、法四国生产，他常年在四国之间飞。

技术上做的事，一句话说得清：**把 SAP 里那些外星表名的数据，映射成「零件、工单、飞机、站位」这些人类概念**，然后做出统一界面，让班组实时看到任务状态。

结果：A350 的制造节奏在当年提升了约 4 倍，空客 CEO 公开把功劳记在 Palantir 头上。这段合作后来长成了空客与 Palantir 共建的 Skywise 平台，而那套「把数据映射成人类概念」的做法（ontology）成了 Foundry 产品最大的差异化功能。

（「约 4 倍」出自当事人自述并有播客交叉印证，空客官方未单独发布过归因数据。完整案例见 [胜 · Airbus 产能爬坡](../04-案例库/胜-airbus-产能爬坡.md)。）

**这个案例对第 6 站有三条直接可用的东西**：

1. **指标锚定决定了造什么**。题目是「每月几架飞机」，所以做的是「班组能实时看到任务状态」；如果题目是「升级数据基础设施」，做出来的会是一个数据平台，然后没人用。**你的第 3 站定的那个指标，此刻正在决定你写的每一行代码**。
2. **把外星表名映射成人类概念，这件事本身就是主要工作量**。不是模型，不是界面，是**让系统里的东西和业务嘴里的东西对上**。第 4 站的数据地图和例外清单，此刻兑现成了这一步。
3. **前线做出来的东西会回流成资产**。ontology 是从这一仗里长出来的。你的第一仗做的那些数据映射、判断卡、提示词，同样会变成第二仗的起点——这是第 8 站要讲的事。

## 八、这一站的判断点（人守的四个）

1. **范围切在哪一刀**。四问自查表能帮你，但最后那一刀是你砍的。
2. **哪个反馈要听，哪个要顶住**。判据：这个反馈指向的是「他干活的真实约束」还是「他觉得这样更好看」。前者立刻改，后者进第二仗清单。
3. **什么时候说**「这版就这样，先用」。没有标准，只有一句提醒：**真实用户周三就该摸到东西，他们的抱怨比你的打磨更能把产品推向正确方向**。
4. **数据里的异常，是脏数据还是真实业务**。这个判断 agent 做不了。「这 200 单的金额是负数」——可能是数据错误，也可能是你们公司真的有一类冲销单。**问人，别猜**。

---

## 九、agent 做什么 / 人判断什么（本站小结）

**agent 做**：调研与技术选型简报、数据剖面与清洗、全部代码与自测、评估集跑批、日报周报与通报草稿、待办跟催、会议纪要。**这一站 agent 承担的执行工作量大概在八成以上**。

**人判断**：

- **去现场**。这是本站最容易丢的动作。agent 越好用，你越容易一整天不离开屏幕，而这一站的胜负手在 D4 和 D9 两天的现场。
- **范围那一刀**。
- **异常的性质**（脏数据 vs 真实业务）。
- **哪句话能对外说**。推进 agent 会把「模型准确率提升到 89%」写进通报，你要知道这句话在你们公司说出去会被谁怎么理解。**对外的每一句话你都要过一遍眼，这一条没有例外**。
- **停手的时刻**。

## 十、这一站的过关检查

- [ ] D0 数据实际到手（不是承诺到手），Eval 已定稿
- [ ] D1 目标对齐会开了，纪要里有那个数字
- [ ] D3 结束前端到端跑通了一条真实链路
- [ ] **D4 给真实用户看了半成品**，且记下了至少 5 条抱怨
- [ ] 范围切割卡四问全答「是」
- [ ] 第一仗期间**一个需求都没加**，第二仗清单在维护
- [ ] 结果送回了用户原来干活的地方（旧入口）
- [ ] D9 用户试运行一整天，你在场，卡壳记录不少于 10 条
- [ ] **D10 由用户自己操作演示**，你在旁边不出手
- [ ] 评估集在这两周里至少跑了 5 次，分数曲线留档
