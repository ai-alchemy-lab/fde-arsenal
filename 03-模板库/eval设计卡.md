# Eval 设计卡（W1 选 尾 / W2 造 前 · 先定什么算好，再动手）

## 权威出处

- Louis Dorard 的 Machine Learning Canvas（OWNML，2015 年起，现行 v1.2）。经典十格是 Value Proposition、Data Sources、Prediction Task、Features、Offline Evaluation、Decisions、Making Predictions、Collecting Data、Building Models、Live Evaluation and Monitoring。作者自述这张纸回答的是四件事："what to predict, what decision it feeds, what data it needs, and what getting it wrong costs."（预测什么、喂给哪个决策、需要什么数据、错了的代价是什么）
  官方页与多格式模板下载：<https://www.ownml.co/machine-learning-canvas>
  GitHub：<https://github.com/louisdorard/machine-learning-canvas>
  可核对的印刷版 PDF：<https://ml4design.com/assets/material/MachineLearningCanvas.pdf>
- **许可**：原版为 CC BY-SA 4.0，允许合法改编再发布，注明出处即可。本卡是它的改编版，**同样以 CC BY-SA 4.0 发布**。

**我们改了什么**

原版十格里，我们只取 Offline Evaluation、Live Evaluation、Decisions 三格，加上"错了的代价是什么"那一问，其余七格由一页立项书和任务拆解卡承担，避免一张纸问二十个问题最后一格都填不实。原版假设房间里有一支 ML 团队和一批带标注的数据；我们面对的是一个业务方拍着桌子说"感觉还行"的会议室，所以第一块整个是新加的：把"什么算好"从业务方嘴里逼出来，落成一句他自己的原话加三个反例。评估集抽样表、judge 提示词骨架、阈值决策格三块也是原版没有的——ML Canvas 写在 LLM 当裁判成为常规做法之前。

## 第一块：和业务方一起定义什么算好

这一块必须当着业务方的面填，一个人填的不算数。

```
一、这个输出喂给谁的哪个决策
　　使用者（人名/岗位）：＿＿＿
　　他看到输出之后要做的动作：＿＿＿（写动词，不许写"参考"）

二、错了的代价
　　答错了谁承担：＿＿＿
　　一次错的代价大概多少（钱/时间/关系）：＿＿＿
　　两类错误哪个更贵：□ 漏报（该报没报）  □ 误报（不该报报了）
　　业务方必须选一个。答"都重要"的，追问到他选为止

三、"好"的一句话定义（业务方原话，别替他润色）
　　"＿＿＿＿＿＿＿＿＿"

四、三个反例（请业务方当场给，这一格比第三格值钱）
　　1. 这种输出算不合格：＿＿＿
　　2. 这种输出算不合格：＿＿＿
　　3. 这种输出算不合格：＿＿＿
```

**为什么要三个反例**：正面定义人人都会写，写出来一律是"准确、有用、专业"。反例才暴露真实标准，而且反例可以直接变成评估集里的样本。

## 第二块：评估集抽样表

不许拿"手边现成的几条"当评估集。按下表分层抽。

| 分层 | 占比 | 从哪抽 | 抽多少 | 谁来标 |
|---|---|---|---|---|
| 日常主流 | 60% | 近 3 个月的真实工单/单据，随机 | | |
| 边角情况 | 20% | 字段缺失、格式异常、跨部门的那些 | | |
| 历史出过事的 | 10% | 投诉记录、返工记录、事故复盘 | | |
| 故意刁难 | 10% | 你和业务方一起编的极端输入 | | |

**四条纪律**

1. 50 条起步。不到 50 条，"效果不错"这四个字不许出口
2. 评估集一旦定稿就冻结。改了要留版本号，不然前后两次分数没法比
3. 评估集绝对不能进提示词，也不能拿去调模型。泄题的评估集等于没有
4. 标注口径写下来，两个人独立标同样 20 条，对不上的先统一口径再往下走

## 第三块：judge 提示词框架

批量评估交给 LLM 当裁判，但裁判本身要先被校准。骨架直接抄：

```
你是【业务领域】的资深审核员。判断下面这条输出是否合格。

【输入】用户的原始问题 / 单据：{{input}}
【输出】系统给出的回答 / 判定：{{output}}
【参考】人工认可的正确答案（如有）：{{reference}}

按三个维度分别打分，每个维度只能给 0 或 1：
1. 事实正确 —— 1 分的标准：＿＿＿  0 分的标准：＿＿＿
2. 决策可用 —— 1 分的标准：＿＿＿（使用者看完能直接做那个动作）  0 分：＿＿＿
3. 说人话 —— 1 分的标准：＿＿＿（用一线的词，先给判断再给依据）  0 分：＿＿＿

拿不准的维度标 uncertain，不要硬给分。

输出 JSON：{"事实正确":0/1/"uncertain","决策可用":...,"说人话":...,"理由":"一句话"}
```

**校准动作**：先人工标 20 条，再让 judge 跑同样 20 条，比对一致率。**一致率低于 80% 时改的是 judge，不是模型**。很多人在这一步搞反了，拿一个没校准的裁判去调模型，越调越偏。

judge 标 uncertain 的那些，全部转人工看。uncertain 比例超过 20%，说明第一块的"什么算好"没定清楚，回去重填。

## 第四块：阈值决策格

分数出来之后，系统该做什么动作，要在上线前写死。

| 分数区间 | 系统动作 | 谁承担后果 |
|---|---|---|
| 高 ＿＿ 以上 | 自动执行并写回 | |
| 中 ＿＿ 到 ＿＿ | 给人看，人点确认才执行 | |
| 低 ＿＿ 以下 | 转人工，系统不给建议 | |
| 无法判断 | 明确拒答，说明缺什么 | |

**每一格的"谁承担后果"必须有名字**。没名字的格子，出事那天全公司都会说"这是 AI 干的"。

**拒答是一等公民**。宁可拒答也不要瞎猜——老师傅被坑一次，这个系统在他那里就永久死亡。

## 上线之后：live evaluation

- 每周从真实输出里随机抽 20 条重新评，分数掉了要报警
- 分数没掉但用户在减少，说明"什么算好"当初就定错了，回第一块重来
- 每月把新出现的失败样本补进评估集，版本号加一

## 人的判断点

⚠️ 第一块 AI 填不了。"什么算好"是一个业务方和你在同一个房间里、互相看着对方眼睛才能定下来的东西，它一半是技术标准，一半是他愿不愿意在出事那天替这个系统说话。

⚠️ 还有一件事没有模板：业务方给的"好"的定义，和一线用户心里的"好"经常不是一个东西。两边都问，不一致的时候以一线为准，然后拿一线的版本回去说服业务方。
