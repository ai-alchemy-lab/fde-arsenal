# MVD 范围切割卡（W2 · 造）

## 权威出处

- Alistair Cockburn 的行走骨架，这张卡最精准的祖先（收于《97 Things Every Software Architect Should Know》第 60 篇 "Start with a Walking Skeleton"，O'Reilly，2009）。原文定义是"一个执行小的端到端功能的微小实现，它不必用最终架构，但必须把主要架构组件串起来"。<https://www.oreilly.com/library/view/97-things-every/9780596800611/ch60.html>
- Basecamp《Shape Up》的 Appetite、断路器与锤范围（Ryan Singer，2019，全书免费在线）。先定愿意花多少时间再把方案锤进去，固定时间可变范围；周期结束没做完的东西不自动滚入下个周期。<https://basecamp.com/shapeup>
- Palantir Ontology 的三个原语（官方文档）。Object Type、Link Type、Action Type——Action Type 的存在意味着 Palantir 把"写回"当成一等公民，一个只能查询不能改变世界状态的 ontology 是不完整的。<https://www.palantir.com/docs/foundry/ontology/core-concepts>

**我们改了什么**

Cockburn 的骨架讲的是技术架构端到端打通，我们换成业务链路端到端打通——国内 AI 落地很少死在架构上（模型是买的、云是现成的），死在数据没接真的、结果没写回业务系统。骨架的关节因此从"架构组件"换成了"数据 → 决策 → 动作"。Shape Up 的 6 周改成 30 天，因为国内老板的注意力周期是月度经营会；它的锤范围靠 shaper 的直觉，内部 FDE 是新手没有直觉，所以外化成四问自查表。断路器改成"第二仗清单 + 一句可照念的话术"，因为在国内拒绝老板的社交成本极高，断路器需要一层给面子的外壳。Palantir 用产品架构强制写回，我们用检查表强制写回，理由一样：只读的系统不改变任何人的工作，也就不产生任何采纳。

MVD（最小可行部署）的军规是**缩小范围，不缩小价值**：可以只做一个部门、一类单据，但必须打通从数据到结果的完整链路。这张卡帮你判断每一刀切得对不对。

## 切割自查（每次砍范围前过一遍）

| 问题 | 答"是"才能砍 |
|---|---|
| 砍掉这块后，从真实数据进、到业务结果出的链路还完整吗？ | □ |
| 砍掉后，剩下的部分还是真实用户的真实工作流吗（不是演示动线）？ | □ |
| 砍掉的是"覆盖面"（更多部门/单据/场景），而不是链路中的一环？ | □ |
| 30 天后要扩大时，砍掉的部分能原样加回来（不用重构）？ | □ |

## 正反例

✅ **好的切法**（缩覆盖面）：只做华东区的退货单；只做一种设备型号的排障；只服务采购部的一个科室。
❌ **坏的切法**（断链路）：先不接真实数据，用样例演示；先做查询不做写回，"下一期再打通"；界面先糊弄一下，"能看就行"（真实用户第一眼就流失）。

## 加需求的应对

W2 期间用户和老板一定会说"能不能顺便加个 X"。标准动作：

1. 当面记进「第二仗清单」（让对方看到被记录）
2. 回一句："这个值得做，但加进这两周会把死线冲掉。第 30 天复盘时它是扩大方案的第一候选。"
3. **凡是不影响本次链路完整性的新需求，一律不进本期**。零例外——例外一次，死线就名存实亡。

⚠️ **人的判断点**：什么时候说"这版就这样，先用"。追求完美是 W2 最大的敌人——真实用户周三就该摸到东西，他们的抱怨比你的打磨更能把产品推向正确方向。
