# Dev 与 Delta：Palantir 的双引擎工程模型

## 来源信息

- **原文**：Dev versus Delta: Demystifying Engineering Roles at Palantir
- **出处**：Palantir 官方博客（blog.palantir.com，托管在 Medium），2019 年 4 月 8 日发布
- **作者**：Bruno Pontes Soares Rocha 博士，Palantir 工程师招聘负责人（Hiring Manager），本人先后做过 FDSE、国际政府客户技术负责人、商业客户前线、产品研发。文章形式是他向全球各办公室的同事收集问答
- **说明**：本文为深度导读，非翻译。基于原文全文提炼

**一句话总评**：这是 Palantir 官方对自家工程组织结构最系统的一次自我解剖——Dev 造平台、Delta 用平台打仗，两边靠代码回流和人才轮换连成闭环，任何想复制 FDE 模式的公司都绕不开这套双引擎设计。

## 逐节导读

### 一、名词解释：Dev 和 Delta 从哪来

Software Engineer 和 Forward Deployed Software Engineer 是 Palantir 人数最多的两个工程岗位，内部叫 "Dev" 和 "Delta"。Delta 这个名字是早期遗产：当年 Business Development（业务拓展部门）的每个团队都用 NATO 字母表命名，Delta 是其中之一，后来成了 FDSE 的统称。

**Dev**（软件工程师）：属于 Product Development（产品研发）部门——Palantir 四大部门之一（另外三个是 Business Development、Internal Development、Sales）。Dev 所在的团队端到端拥有一个平台组件，比如 Foundry 的存储基础设施、Gotham 的 UX。日常是写代码 + 和团队做设计与架构决策，而这些决策影响的代码最终会部署给许多不同客户、支撑许多不同用例。文中的 Helen（纽约，Foundry 某团队后端负责人）强调没有经理告诉她做什么和怎么做——她和产品经理、设计师、前后端工程师一起决定为了产品愿景需要什么架构改动。

**Delta**（FDSE）：属于 Business Development 部门，使命是"为客户达成技术性成果"。一个 Delta 团队直接服务一个客户，工作是部署和定制 Palantir 平台去解决关键业务问题，**成功的度量单位是客户目标上的影响**。文中举例：制造业客户想降低产线次品率，Delta 就用 Palantir 产品 + 各种语言 + 开源工具 + 行业标准构建工具 + 自己的创造力，做出真正能挪动这个指标的方案。

全文最值得记住的一句总结：**Dev 是"一个能力、许多客户"，Delta 是"一个客户、许多能力"**。

### 二、Delta 不是顾问

文章借多位一线 Delta 之口，从三个角度拆掉"Delta = 咨询顾问"的误解：

1. **交付物不同**（Elisa，纽约）：顾问通常交付一次性的分析、建议或针对单一问题的方案；Palantir 是和客户一起构建让客户能持续自我改进的长期方案。
2. **手段不同**（Dyon，阿布扎比）：Delta 的关键差异是真的在部署现成的软件产品去达成客户成果，不是写报告。
3. **技术含量不同**（G.M.，圣保罗）：Delta 做的工程和技术工作远多于顾问，需要的技术深度在咨询行业里很少见。

### 三、Delta 给核心产品写代码：回流机制的细节

这一节是全文含金量最高的部分之一。多位 Delta 提到他们经常把代码贡献回核心产品。规则大致是：

- 如果挡在客户成果面前的是平台缺一个功能、缺一个能力或有个 bug，那 Delta 自己动手做可能是合理的
- 但**必须和产品团队协调**（Ian，华盛顿，从 Delta 转成 Dev 的人特别强调这点）
- 较大的功能请求要先对着产品路线图验证、并被纳入路线图
- 开发过程中要和产品团队保持持续沟通：问代码问题、请对方验证和 review 改动

也就是说，前线可以直接改产品，但不是野路子——有一套"先对齐路线图、开发中持续 review"的协作协议兜着。

### 四、两边的日常长什么样

**Dev 的日常**：Ian 在做 Gotham 平台一个试点阶段的新能力，感觉像在小创业公司当开发——和一个正在客户那里试点该能力的团队手拉手，快节奏出新功能，同时还要为这个年轻产品的未来做正确决策。Helen 作为后端负责人，每周花几小时做优先级排序和进度追踪，**定期会见客户前线团队，听他们最高优先级的产品需求，判断怎么排进路线图**，其余时间写代码、review 代码、在 Slack 答疑、处理支持工单。注意：连 Dev 的日常都深嵌着与前线的接口。

**Delta 的日常**：G.M. 说他的日常是按月变的——有几周像典型工程师一样整天开发和 review 团队代码，另几周主要在和客户规划项目未来、或和用户确认做出来的东西是否好用。Dyon 的一周更具体：**几天在客户现场**（一部分时间开技术或业务干系人的会，其余时间监控、调试、部署、配置软件），回办公室的时间写小的代码改动、review PR、研究和规划客户方案，剩下的时间用邮件/视频会议对接内部支持团队、产品团队和分布在多个远程办公室的直接下属。

### 五、各自需要什么技能

**Dev**：Matt（帕罗奥图）总结三件事——把产品反馈综合成技术策略、在多方干系人之间有效排优先级、用干净可维护的代码实现功能。Ian 补充：除了标准工程师技能，还需要在扁平组织里生存的技巧，以及比一般工程岗位更高的共情和人际能力。

**Delta**：Elisa 给出了本文最值得抄作业的三条：

1. **Technical decomp**（技术分解）：拿到一个高层次的业务问题，能层层分解并设计方案——从业务问题一路理解到解决它所需的每一行代码。
2. **自主性 + 强技术直觉**：团队小、节奏快，必须能自己搞定事情——自学新语言、琢磨怎么写插件、调试平台问题，全靠技术直觉撑速度。
3. **思辨力**：能分析局面并形成自己的判断。最典型的日常决策：客户要的功能，是花时间做进核心平台，还是做个能更快交付的定制版？这个权衡每周都在发生。

Katherine（华盛顿）的说法更妙：FDSE 群体像个"艺术家聚落"，每个人靠独特的技能组合创造价值，很难列出统一的成功技能清单——但高用户共情、理解业务战略的能力和意愿、创造性解题、独立性是成功者的公约数。

### 六、他们最喜欢什么、干过什么酷事

喜欢的部分：Dev 这边是"技术难 + 真的在乎自己造的东西给谁用、成什么事"（Ian），以及"发现一个普遍问题、在核心产品里一次性解决、赋能全公司"（Matt）。Delta 这边是"永远在学习、永远在舒适区外"（G.M.）、"看着客户用我们造的东西解决了大难题"（Elisa）、"从个人贡献者转为带团队后获得的全局视角，以及把业务战略翻译成技术执行"（Katherine）。

酷事清单很能说明这两个角色的现场感：Dev 参观过刚下线的空客 A350、去新加坡轮岗三个月；Delta 在汽车厂坐在车里过颠簸测试track、给某国防军种的参谋长演示软件、台风海燕后两周内奔赴菲律宾用数据工具调度人道主义物资、接到通知两周后被派驻巴西——一年后用驻地学会的葡萄牙语给客户工程师讲架构。

### 七、结论：两个角色之间人是流动的

对纠结投哪个岗位的人，作者的回答是：**两个角色之间流动很多，公司鼓励换视角**。Matt 在法国做了约六个月 FDSE，然后到帕罗奥图做了两年 Foundry 的 Dev，他说前线经历深刻影响了他做产品时的优先级判断。Katherine 认为 Dev 去一线亲身体会用户的处境是好事。Dyon 干了七年 FDSE，头衔没变但角色内涵一直在变，身边有人从客户前线转到纯产品研发、甚至转到 HR。

作者本人就是活例子：FDSE（中东、北欧）→ 国际政府客户的跨国技术负责人 → 纽约商业客户前线 → 产品研发团队做人才和招聘。最后总结 Palantir 工程文化的三个公共线索：最小化层级、协作环境、死磕客户的关键成果。

## 对 FDE 培养体系设计的启示

1. **FDE 模式是"双引擎 + 两条管道"，缺一不可**。Dev 造平台、Delta 打前线只是表层；真正让飞轮转起来的是两条管道——代码回流管道（前线改动经路线图对齐进入核心产品）和人才轮换管道（Dev 与 Delta 互转）。训练营如果只教"怎么当前线工程师"而不教这两条管道的协作协议，学员进企业后会变成孤岛。
2. **"Technical decomp"应该是核心考核科目**。Elisa 那条"从业务问题分解到每一行代码"是 FDE 区别于普通工程师和普通顾问的分水岭能力。可以设计成标准题型：给一个模糊的业务目标（如"降低次品率"），要求学员输出从指标定义到系统架构到代码模块的完整分解树。
3. **教会学员做"平台 vs 定制"的权衡决策**。Delta 每周都在决定：这个需求做进平台还是做快速定制？这是有练习价值的判断题——训练营可以在项目中植入这类分叉点，要求学员写出权衡理由（交付速度、复用价值、维护成本、路线图冲突）。
4. **前线角色的"成功度量"必须绑客户指标**。Palantir 给 Delta 的 KPI 不是代码量或交付物数量，而是客户业务指标的变化。训练营的项目验收也应该定义成"客户指标是否移动"，逼学员从第一天就想清楚衡量什么。
5. **招人别找单一画像，找"艺术家聚落"**。Katherine 的比喻提示：FDE 团队的价值来自技能组合的多样性。孵化器选学员时与其卡统一标准，不如刻意混搭背景（硬件、数据、咨询、行业专家），再用共同的底盘训练拉齐——这更接近 Palantir 的真实人才结构。
