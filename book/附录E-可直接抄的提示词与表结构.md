# 附录 E　可直接抄的提示词与表结构

这一份是工作台，不是读物。

正文里凡是写着"结构见附录 E""指令原件在附录 E"的地方，东西都在这儿。它们全部来自第 7 章和第 8 章，是那两站里最有转手价值的部分——评估集长什么样、让大模型当裁判的提示词怎么写、四个 agent 的任务指令怎么下。放在正文中段，非技术读者会在这里弃章，而真正要用它的人反而找不到；放在这儿，你打开书直接翻到最后。

## 怎么用这一份

**一、先读正文，再抄这里**。这里给的是实物，判断在正文。为什么 `gold_reason` 这一列不能省、为什么安全维度不能参与加权平均、为什么代码指令必须一次一个小目标——这些理由写在第 7 章第五、六节和第 8 章第五节，抄之前先把那几页看完。不看理由直接抄，你会把它们改坏而不自知，因为每一条约束看起来都像是可以省掉的啰嗦。

**二、改哪几处，一处不能少**。

下面每一件都标了"必改"。它们是这些模板里唯一带着别人公司体温的部分，不改的话你测的是别人的业务。

| 件 | 必改的地方 |
|---|---|
| 评估集字段结构 | `layer` 的分层名称按你自己的分层表来；`is_redline` 那几条红线必须由你们的业务负责人亲口给，不能由你代拟 |
| judge 一号（判对错） | 整段【判定规则】。这是第 7 章第三节那场 90 分钟会议的产出，不是可以从别人书上抄来的东西。规则下面要署业务方的名字和版本日期 |
| judge 二号（判好坏） | 四个打分维度本身。维度必须长在你自己的现场上，抄一份通用评测维度回来打分，你会得到一个漂亮的分数和一个没人用的系统 |
| 四段 agent 指令 | 每段开头的【背景】和【约束】。技术路线可以通用，你们公司数据不出内网、你只有一个人、两周内要给真人用——这三件事只有你知道 |

**三、不能改的地方也标出来了**。每件下面有一节"这几句别删"，删掉它们，模板会安静地失效——不会报错，只会给你一份看起来正常的错东西。

**四、许可**。全部可自由取用，注明出处即可。评估集字段结构与 judge 提示词骨架改编自模板库的《Eval 设计卡》，那张卡以 CC BY-SA 4.0 发布，再改编要沿用同一许可。

## E1　评估集字段结构

一个文件，一行一条。对应第 7 章第五节。

| 字段 | 说明 | 示例 |
|---|---|---|
| `id` | 唯一编号 | `EV-0137` |
| `layer` | 属于哪一层 | 边界 |
| `input` | 完整原始输入，不要预处理，要脏的 | 邮件正文原文，含错别字和排版 |
| `context` | 这条的背景信息 | 该客户 30 天内第 3 次来信 |
| `gold_label` | 标准答案，业务方重标后的 | 类型等于投诉，紧急度等于高 |
| `gold_by` | 谁标的 | 李国强 |
| `gold_reason` | 为什么是这个答案，一句话 | 提到了"再不解决就投诉到总部" |
| `history_label` | 当时人工的实际处理结果 | 类型等于咨询，紧急度等于中 |
| `is_redline` | 是否红线样本 | 是，红线 1 |
| `notes` | 备注 | 附件是一张手机拍的照片，很糊 |

一条填好的完整样例：

```
id: EV-0137
layer: 边界
input: "上次那个单子到现在还没给我回话，我这都第三回问了。你们要是再不给个说法我就打12315了。订单号 A2026081100731"
context: 该客户 30 天内第 3 次来信；订单金额 3,280 元；前两次均被分为"咨询-物流"
gold_label: 类型=投诉，紧急度=高
gold_by: 李国强
gold_reason: 出现"第三回"（重复来信）+ 明确的监管投诉威胁（12315），任一条件成立即为投诉-高
history_label: 类型=咨询-物流，紧急度=中
is_redline: 是（红线1：提到监管渠道未判为投诉）
notes: 这条历史处理是错的，当时的客服只看了订单号
```

### 这几句别删

`gold_reason` 这一列。它是几乎所有人省掉的一列，而第 7 章给了它三个理由：标准可被审计、它是下面那个 judge 提示词的原料、它能暴露标注者自己的不一致。

`history_label` 和 `gold_label` 两列并存。上面这条样例里两者不一样，这正是让业务方重标一遍的全部意义。你要是直接把历史标签当答案，你的系统会学会犯同一个错误，而且犯得比人更稳定、更快、更理直气壮。

## E2　judge 一号：判对错

用于分类、抽取、判定这类有标准答案的任务。对应第 7 章第六节。

```
你是一名客服工单质检员。你的任务是判断一条自动分类结果是否正确。

【判定规则】（由恒美家居客服中心主管李国强定义，2026-09-01 版）
1. 类型判定优先级：投诉 > 售后 > 咨询。同时符合多类时，取优先级最高的。
2. 满足以下任一条件，即为"投诉"：
   - 出现监管或第三方渠道字样（12315、消协、市监、起诉、媒体、投诉到总部）
   - 同一客户 30 天内第 3 次及以上就同一订单来信
   - 出现明确的情绪表达且指向服务过程（"太差了""气死我了""没人管"）
3. 紧急度判定：
   - 高：投诉类；或涉及金额 > 50000 元；或提到人身安全
   - 中：售后类且客户已等待 > 48 小时
   - 低：其余

【输入】
原始邮件：{input}
背景信息：{context}

【待评判的系统输出】
类型：{pred_type}
紧急度：{pred_urgency}

【标准答案】
类型：{gold_type}
紧急度：{gold_urgency}
判定依据：{gold_reason}

【你的任务】
严格按下面的 JSON 输出，不要输出任何其他内容：
{
  "type_correct": true 或 false,
  "urgency_correct": true 或 false,
  "verdict": "完全正确" | "类型错" | "紧急度错" | "都错",
  "which_rule": "系统输出违反或遗漏了上面第几条规则，写规则编号；若正确写 '-'",
  "one_line": "一句话说明系统为什么判错，不超过30字；若正确写 '-'"
}

【重要】
- 只依据上面的判定规则，不要用你自己的常识补充规则。
- 如果标准答案本身看起来违反了判定规则，在 one_line 里写 "疑似标注问题：..."，
  并把 type_correct 按规则判定，而不是按标准答案。
```

### 这几句别删

【重要】里的**第二条**，也就是"疑似标注问题"那一条。第 7 章说过它是整个提示词里最重要的设计：它让裁判在跑批的同时替你查标注错误。

【重要】里的**第一条**，"不要用你自己的常识补充规则"。不写这一句，裁判会把它对客服行业的通识补进来，于是你测的就不再是你的规则，而是它的常识。

**输出格式那一段**。不规定格式，你拿到的会是一段散文，没法统计。JSON 是一种把结果写成"字段名加值"的文本格式，程序能直接读，你不需要懂它怎么写，照抄结构即可。

## E3　judge 二号：判好坏

用于生成类任务，比如排障建议、回复草稿、纪要摘要。这类任务没有标准答案，只能多维打分。对应第 7 章第六节。

```
你是一名资深设备检修工程师，有 20 年现场经验。
请对一条 AI 生成的排障建议打分。你的评价标准是"一个刚入职半年的工程师，
拿着这条建议站在故障设备前，能不能干活"。

【故障现象】{input}
【设备背景】{context}
【AI 给出的建议】{output}
【老师傅的参考答案】{gold}

请在四个维度上各打 1-5 分，并给出一句理由：

A. 决断性：第一句话有没有给出一个明确的、最可能的判断？
   5 分 = 第一句就是"八成是X，先做Y"
   3 分 = 给了判断但埋在第三段之后
   1 分 = 通篇是"可能有多种原因，建议逐项排查"
B. 可执行性：一个新人能不能照着做？动作是否具体到"拧哪颗螺丝、看哪块表"？
   5 分 = 每一步都有明确的对象和动作
   1 分 = 只有"检查通讯链路"这种层级的表述
C. 安全性：有没有遗漏高风险分支？有没有把高风险情况的提示写在显眼位置？
   5 分 = 明确写出"如果同时出现Z，立刻停机并叫设备科"
   1 分 = 完全没提高风险分支
   【注意】本维度打 1 或 2 分的，整条直接判为不合格，无论其他维度多少分。
D. 像人话：读起来像老师傅说的，还是像规程手册？

严格按 JSON 输出：
{
  "decisiveness": 1-5, "decisiveness_why": "...",
  "actionability": 1-5, "actionability_why": "...",
  "safety": 1-5, "safety_why": "...",
  "human_like": 1-5, "human_like_why": "...",
  "hard_fail": true 或 false,
  "worst_dimension": "四个维度里最差的那个的字母"
}
```

### 这几句别删

**C 维度里那句"整条直接判为不合格，无论其他维度多少分"**。安全维度不能参与加权平均，因为平均会把它抹平：一条 A、B、D 都是 5 分而 C 是 1 分的建议，加权后是 4 分，看起来很好，实际是会出事故的那一条。

**`worst_dimension` 这个字段**。跑完一批按它聚类，你会得到一句很有用的话：这一版最该修的是可执行性，一百二十条低分里有七十条卡在这。它把"分数不高"变成了"去修哪儿"。

### 别忘了校准

这个裁判在用之前必须做一次对齐测试，一致率不到线不许上批。测法、那条线定在哪、以及不一致的条目怎么读，在第 7 章第六节末尾。

## E4　四段 agent 任务指令

对应第 8 章第五节。四个岗位各一段：调研、数据、代码、推进。

### 调研 agent

```
背景：制造企业客服工单自动分类，12 个类别，中文，日均 2000 条，
      历史数据 6 个月，标注质量一般（人工历史标签错误率约 15%）。
约束：不能用外部 API（数据不出内网），可用本地开源模型，
      我一个人做，两周内要有能给真人用的东西。
任务：给我三条技术路线，每条包含：
  1) 大致做法（不超过 5 行）
  2) 两周内做出来的可能性（高/中/低）和理由
  3) 已知的失败模式——具体是什么情况下这条路会崩
  4) 需要我提前确认的一件事
不要给我通用的最佳实践列表。不要推荐需要标注 10 万条数据的方案。
```

**别删最后那两句**。不写它们，你会拿到一份维基百科式的技术综述。约束条件写得越具体，调研 agent 的价值越高，这一点和你带一个新人一模一样。

### 数据 agent

```
数据：附件是退货单主表 3 万行、明细表 12 万行的切片。
先做常规剖面：每个字段的空值率、取值分布、极值、时间分布。
然后重点回答这五个问题：
  1) 哪些字段在某个时间点前后行为明显不同？（可能有口径变更）
  2) 哪些字段名义上是枚举，实际出现了未文档化的取值？
  3) 主表和明细表关联，有多少条关联不上？关联不上的有什么共同特征？
  4) 有没有明显是"被挪作他用"的字段？（比如备注栏里塞了结构化信息）
  5) 如果我要按"华东区 + 2026 年 + 退货类"取子集，实际能取到多少条？
最后列出：你认为我应该去问业务方的三个问题。
```

**别删最后那一行**。它是这段指令里最值钱的一句，因为它把 agent 从"回答我问的"变成"告诉我该问什么"。

### 代码 agent

```
目标：把 data/eval_v1.jsonl 里的 300 条邮件跑一遍分类，
      输出 pred.jsonl，字段 id / pred_type / pred_urgency / confidence。
约束：用 prompts/classify_v3.txt 里的提示词，不要改它。
      失败的条目不要跳过，写进 failed.jsonl 并记录原因。
完成后：跑 scripts/score.py，把分层准确率贴给我。
```

**别把它换成"帮我做一个客服分类系统"**。不是因为它做不了，是因为它做出来的东西你没法判断对不对。你失去了判断点，就等于把这一仗交出去了。

另外一条硬约束在第 8 章第九节：保留集必须放在代码 agent 没有读权限的目录里。

### 推进 agent

```
输入：今天的工作记录（见下）。
产出三样：
1) 给业务群的一句话通报，格式："今天根据 X 的反馈改了 Y。"
   要具体到人名和改动内容，不要写"优化了系统性能"。
2) 明天要办的三件事，按优先级。
3) 需要别人配合的事项清单，每条写清：找谁、要什么、什么时候要。
纪律：通报里不出现"赋能""闭环""智能化"这类词。
      不确定的进展不要写成已完成。
```

**别删"今天根据谁的反馈改了什么"这个格式**。它不是为了好看。它每天在业务群里公开确认一件事：这个系统是按你们说的在改。第 9 章会讲，这句话每天发一次，两周之后的效果比一场上线宣讲会强得多。

## E5　黑话对照表

对应第 7 章第十节难题二。五列，三条填好的例子。这张表不该由你坐在工位上编，它的原料是第 4 站跟班带回来的例外清单和判断卡。

| 现场说法 | 规范名 | 谁这么说 | 会和什么撞车 | 出处 |
|---|---|---|---|---|
| 大罐子 | 3 号中和釜 | 二分厂夜班 | 一分厂的"大罐子"指储气罐 | 8/14 跟班，张师傅 |
| 老李那台 | CNC-07 | 加工车间全员 | 李师傅 2024 年已调岗 | 8/15 跟班 |
| 走单 | 紧急插单流程 | 计划科 | 财务口径里"走单"指走账 | 访谈，计划科王工 |

### 这几句别删

**第四列"会和什么撞车"**。这是这张表真正的价值所在，理由在第 7 章第十节：单个黑话不难猜，撞车的黑话才会让系统给出一本正经的错答案。这一列一旦填出内容，你就知道那个字段必须先做消歧。

**第五列"出处"**。这张表一定会被质疑，一定有人说"我们厂没人这么讲"，你要能回一句这是 8 月 14 号夜班张师傅的原话。

**表做出来之后的两个用处**。judge 的判定规则里要显式带上它，别指望模型认识"那个大罐子"；同时它本身就是给业务方看的证据，证明你真的下过现场。我见过这张表在验收会上比准确率数字管用。
