# 第 8 章 造与测

## 一、D4 早上那条微信

"再给我两天，现在这个样子拿出去太丢人了。"

发消息的是一位刚开始做第一仗的内部 FDE，前财务系统的产品经理，转过来做 AI 落地不到三个月。那天是他两周冲刺的第四天，按节拍表，那天下午他要把手上那个半成品第一次拿给真实用户看。

他说的是实话。当时那个东西界面是默认样式，没有登录，异常输入直接报错，跑一次要等七秒，十二类工单里只跑通了三类。任何一个受过产品训练的人看到它，第一反应都是这东西不能见人。

我回了他两句。第一句是：你今天下午必须给他看。第二句是：他会说的那些话，你现在已经猜到了几条？

他列了三条：界面太丑、太慢、类别不全。

下午看完，用户的反馈是这样的。第一条，你这个结果出来之后我得复制粘贴到工单系统里，那我还不如自己填。第二条，我看不出来它为什么这么判，我不敢直接用。第三条，能不能把上一条也显示出来，我们判这个的时候要看前面那单。

他猜的三条，一条都没中。而用户提的三条里，第一条要改的是交付形态，第二条要改的是输出结构，第三条是一条他从来不知道的业务规则。这三条如果拖到 D9 才知道，这一仗就结束了。

界面丑这件事，用户一个字都没提。

这一章讲的就是这两周怎么过。它是全书里 agent 承担最多的一站，八成以上的执行工作可以交出去，也正因为如此，它是最容易做得很顺、顺到一整天没离开屏幕的一站。这两件事是同一件事的两面。

## 二、MVD：裁判不一样

这两周要造的东西叫 MVD，最小可行部署。它和 POC、MVP 都不一样，区别不在做多少，在谁当裁判。

| | POC | MVP | MVD |
|---|---|---|---|
| 目的 | 证明技术可行 | 验证市场需求 | 证明业务价值 |
| 裁判 | 技术评审 | 早期用户 | 业务现场 |
| 数据 | 样例、脱敏假数据 | 早期用户自带 | 生产数据切片 |
| 及格线 | 能跑通 | 有人愿意用 | 业务指标动了，一线在用 |

一句话记住：**POC 的终点是一次演示，MVD 的终点是一个还在跑的系统**。演示完鼓掌散会的都不算。

三条军规。

### 军规一：只用真实数据，没有例外

第一天就接真实数据切片，第 2 站已经拿到授权，第 4 站已经拿到手。

理由很硬。企业数据的真实难度占了这两周工作量的一大半：外星表名、四种日期格式、同一种缺陷在三个分厂三套叫法、名义上叫"缺陷等级"实际被挪用成备注栏的字段。用样例数据，等于把最难的部分留到最后，而最后你没有时间了。

案例库里那份《败 · POC 陷阱》是这条军规的反面标本。厂商用 300 份格式干净的样例报告，两周做出 POC，演示惊艳，签约走绿色通道；真实数据一接进来全变了，第 12 周只跑通一个分厂的一部分，第 20 周例会没有业务方参加，系统停在会议室里。没有人宣布这个项目失败，它只是安静地从所有人的日程里消失了。

### 军规二：缩小范围，不缩小价值

可以只做一个部门、一类单据、一条产线，但必须打通从数据进到业务结果出的完整链路。

判断标准只有一句：做完之后，公司里有没有一个具体的人，他每天的某个动作因此变了。

这条军规最精准的祖先是 Alistair Cockburn 的行走骨架（Walking Skeleton），收在《97 Things Every Software Architect Should Know》第 60 篇。原文定义是：一个执行小的端到端功能的微小实现，它不必用最终架构，但必须把主要架构组件串起来。

我们改了一个词。Cockburn 讲的是技术架构端到端打通，我们换成业务链路端到端打通。国内 AI 落地很少死在架构上——模型是买的，云是现成的，代码 agent 写——死的是数据没接真的、结果没写回业务系统。所以骨架的关节从"架构组件"换成了"数据到决策到动作"。

### 军规三：锁死期限

期限是纪律工具。它逼你砍需求，逼别人配合，逼双方在完美和能用之间选能用。

这一条借自 Basecamp《Shape Up》里的 fixed time, variable scope：先定愿意花多少时间，再把方案锤进这个时间里，而不是先估工期。以及它的断路器规则：周期结束时没做完的东西，不自动滚入下一个周期。

断路器这条在中国企业里要加一层外壳，因为"没做完就砍掉"这句话直接说出口，社交成本极高。外壳在第六节，是一句可以照念的话。

到期那天只有三个词：继续、调整、停止。

## 三、两周节拍，逐日

节拍参照 Palantir 驻场的真实节奏。他们的部署策略师公开过自己的一天，10 点 15 分在做数据管道，把客户的 ERP 接进一个处理发货差异的应用，13 点 30 分就带着上午刚做的东西进客户迭代会。上午写的代码下午就进会，一周跑四到五个完整循环。

| 天 | 干什么 | 当天的硬约束 |
|---|---|---|
| D0 | 数据切片实际到手，Eval 定稿，范围切割卡填完 | 数据没到手不许开工 |
| D1 | 目标对齐会，业务负责人在场，把成功定成一个数字；下午开始接数据 | 会议纪要当天发出，含那个数字 |
| D2 到 D3 | 打通第一条最窄的端到端链路，丑没关系 | D3 结束必须端到端跑通一条，哪怕只有 10 条数据 |
| D4 | 第一次给真实用户看半成品 | 这一天不许推迟 |
| D5 | 按反馈改；和业务负责人对一次范围还砍不砍 | 周复盘，评估集跑一次 |
| D6 到 D8 | 加固：权限、异常处理、边界情况，把 D4 挨的骂逐条消掉 | 每天下午继续给人看 |
| D9 | 真实用户试运行一整天，你在旁边看着 | 你必须在场，不许远程 |
| D10 | 验收演示，由用户自己操作 | 当场决定下一步 |

这张表里只有两天是不可动的，D4 和 D9。其余每一天的内容都可以按你的场景调，这两天不行。

### D4 为什么不能推迟

到了 D4，东西一定很丑，你一定会想再改两天再给人看。这个念头非常正当，它来自你的职业训练。

不许。三个理由。

**早暴露的问题便宜**。D4 发现方向错了，你还有 6 天；D9 发现方向错了，这一仗结束了。第一节那三条反馈，第一条要改的是交付形态，第二条要改的是输出结构，这两样都是地基级的改动。地基在第四天改，是一天的事；在第九天改，是重做。

**一起改过五轮的用户会把你当自己人**。迭代密度就是信任积累的速度。这不是软性收益，它直接决定第 9 章的采纳率。一个参与过五轮修改的人，在系统出问题的时候会说"这儿还得再改改"，一个只在验收那天见过成品的人会说"这东西不行"。

**你需要他的抱怨，不需要他的赞美**。一个打磨过的成品会得到"挺好的"，一个半成品会得到"这个字太小了我看不清"。后者才是有用的信息。这一条和第 6 章访谈那一节的"不带 demo"看起来矛盾，其实不矛盾：第 4 站不带 demo，是因为那时候你要听的是他的问题，一掏 demo 他就切换成评价你的产品；第 6 站必须带半成品，是因为这时候你要听的正是他对这个具体东西的评价。前一站问的是"你怎么干活"，这一站问的是"这个东西挡了你哪儿"。

丑这件事，你比用户在意得多。第一节那个例子里，用户一个字都没提界面。一线用户对内部系统的审美期待，比你以为的低一个数量级，他们在意的是这东西能不能替他省掉那三分钟的复制粘贴。

### D9 那一天你在旁边看什么

带一个本子，记三样，**只记不说**。这一天你张嘴帮他一次，就浪费了这一天的一部分，因为你帮过的那一步，明天他一个人的时候还是会卡在那里。

每一次他停顿超过 3 秒的地方。那是他不知道下一步该干什么。

每一次他去问别人或者打开另一个窗口。那是你的系统没覆盖到的信息需求。

每一次他绕过系统直接用老办法。那是这个系统在他心里的真实位置。

这三样和第 6 章跟班时看的那五样是同一种观察方法，观察对象从他的旧流程换成了你的新系统。你在第 4 站用它诊断这家公司，在第 6 站用它诊断你自己。

## 四、个体制，不搞配对

Palantir 前线的标准编制是两个人：FDSE 管造，Deployment Strategist 管推。一个对系统能不能跑、跑得稳不稳负责，一个对有没有人用、价值算不算得清、组织里推不推得动负责。这套配对经过了二十年验证。

我们不抄它。内部 FDE 走个体制，一个人，带一支 agent 军团。三条理由。

**配对在企业内部是一种奢侈品**。Palantir 派两个人进场，是因为客户在付钱。你在自己公司里做第一仗，能把一个人的六成时间抠出来，已经是第 2 站打过一场硬仗的结果。要两个人，这个项目大概率立不起来。

**配对解决的问题，内部人本来就没有**。DS 这个角色存在的核心理由是外部人不了解客户组织，他要花大量时间做组织导航、找拍板人、读会议室里的权力结构。而内部 FDE 在第 1 站就是按组织导航这一项挑出来的，他本来就认识这些人。把外部人的分工方案照搬到内部，等于为一个你没有的问题付费。

**2026 年配对里那个"推"的角色，一半的执行工作可以交给 agent**。调研、材料准备、进度跟踪、日报周报、访谈转写与归纳，这些原来占据 DS 大量时间的活，现在是 agent 的活。人留下的是判断和露面。

所以这一站的正确心智不是"我一个人要干两个人的活"，而是：你是这支小队的指挥官，agent 是兵，你是唯一那个负责任的人。

一个必须说清楚的例外：个体制不等于孤军。第 4 站那个被动了奶酪的人、第 2 站那次负责人亲自出面，涉及组织政治的硬仗仍然需要你的负责人露面。**个体制说的是执行编制，不是政治后盾**。

## 五、agent 军团编制：四个岗位

不要用一个通用助手干所有事。分成四个有明确职责、明确输入输出、明确交接物的 agent，理由和企业里分工的理由一样：职责混在一起，质量无法归因。

| agent | 它干什么 | 你给它什么 | 它交给你什么 | 你在这里守什么判断 |
|---|---|---|---|---|
| 调研 agent | 外部检索、同行做法、技术选型、失败案例 | 具体问题加已知约束 | 一页简报、三个可选方案、每个方案的已知坑 | 选哪条路，以及哪些"行业最佳实践"在我们这儿不成立 |
| 数据 agent | 剖面统计、清洗、字段对齐、口径核对 | 数据切片加第 4 站的数据地图 | 字段质量报告、异常清单、可用数据集 | 哪个异常是脏数据，哪个异常是真实业务 |
| 代码 agent | 写、改、测、部署 | 一次一个明确的小目标 | 能跑的东西加它自己的自测结果 | 范围切在哪，什么时候停手说"这版就这样" |
| 推进 agent | 日报、进度跟踪、会议纪要、汇报材料、待办跟催 | 每天的原始记录 | 一句话通报、周报、汇报草稿 | 哪句话能对外说，哪句话不能 |

### 四段可以直接抄的指令

调研 agent 最容易被用废，因为大多数人只会问"XX 怎么做"。正确的下法是给约束。

```
背景：制造企业客服工单自动分类，12 个类别，中文，日均 2000 条，
      历史数据 6 个月，标注质量一般（人工历史标签错误率约 15%）。
约束：不能用外部 API（数据不出内网），可用本地开源模型，
      我一个人做，两周内要有能给真人用的东西。
任务：给我三条技术路线，每条包含：
  1) 大致做法（不超过 5 行）
  2) 两周内做出来的可能性（高/中/低）和理由
  3) 已知的失败模式——具体是什么情况下这条路会崩
  4) 需要我提前确认的一件事
不要给我通用的最佳实践列表。不要推荐需要标注 10 万条数据的方案。
```

注意最后两句。不写这两句，你会拿到一份维基百科式的技术综述。约束条件写得越具体，调研 agent 的价值越高，这一点和你带一个新人一模一样。

数据 agent 的价值在于发现你想不到要问的事。

```
数据：附件是退货单主表 3 万行、明细表 12 万行的切片。
先做常规剖面：每个字段的空值率、取值分布、极值、时间分布。
然后重点回答这五个问题：
  1) 哪些字段在某个时间点前后行为明显不同？（可能有口径变更）
  2) 哪些字段名义上是枚举，实际出现了未文档化的取值？
  3) 主表和明细表关联，有多少条关联不上？关联不上的有什么共同特征？
  4) 有没有明显是"被挪作他用"的字段？（比如备注栏里塞了结构化信息）
  5) 如果我要按"华东区 + 2026 年 + 退货类"取子集，实际能取到多少条？
最后列出：你认为我应该去问业务方的三个问题。
```

最后那一行是这段指令里最值钱的。它把 agent 从"回答我问的"变成"告诉我该问什么"。

代码 agent 的核心纪律是一次一个小目标，且每个目标都要能验证。

```
目标：把 data/eval_v1.jsonl 里的 300 条邮件跑一遍分类，
      输出 pred.jsonl，字段 id / pred_type / pred_urgency / confidence。
约束：用 prompts/classify_v3.txt 里的提示词，不要改它。
      失败的条目不要跳过，写进 failed.jsonl 并记录原因。
完成后：跑 scripts/score.py，把分层准确率贴给我。
```

不要下"帮我做一个客服分类系统"这种指令。不是因为它做不了，是因为它做出来的东西你没法判断对不对。**你失去了判断点，就等于把这一仗交出去了**。

推进 agent 是四个里最被低估的一个。

```
输入：今天的工作记录（见下）。
产出三样：
1) 给业务群的一句话通报，格式："今天根据 X 的反馈改了 Y。"
   要具体到人名和改动内容，不要写"优化了系统性能"。
2) 明天要办的三件事，按优先级。
3) 需要别人配合的事项清单，每条写清：找谁、要什么、什么时候要。
纪律：通报里不出现"赋能""闭环""智能化"这类词。
      不确定的进展不要写成已完成。
```

那句"今天根据谁的反馈改了什么"的格式不是为了好看。它每天在业务群里公开确认一件事：这个系统是按你们说的在改。第 9 章会讲，这句话每天发一次，两周之后的效果比一场上线宣讲会强得多。

### 你在这个编制里的一天

| 时段 | 你在干什么 | agent 在干什么 |
|---|---|---|
| 早 30 分钟 | 看昨天的跑批结果和用户反馈，定今天的一个目标 | 昨晚的批处理跑完了，日报在等你 |
| 上午 | 下指令、看中间结果、做判断 | 数据和代码在干活 |
| 中午 | 去现场，和用户吃个饭，看他们用 | 后台继续跑 |
| 下午 | 给用户看半成品，挨骂，当场记 | 推进 agent 在整理上午的记录 |
| 晚 30 分钟 | 决定明天改什么，发一句话通报 | 跑今晚的评估集 |

中午那一格和下午那一格不能被 agent 替代，也是最容易被跳过的两格。一个人带 agent 军团最大的风险不是做不出东西，是做得太顺，顺到你一整天都没离开屏幕。

这个风险在 2023 年不存在。那时候你被迫离开屏幕，因为代码要自己写、材料要自己做、数据要自己洗，写不动的时候你会站起来走走，走到隔壁部门去。现在这些事都有人替你干了，屏幕上永远有东西在动，永远有下一步可以推进。这是这一站最隐蔽的一个陷阱：它不表现为失败，它表现为效率很高。

## 六、范围切在哪一刀

这是这一站最重要的判断，用模板库的《MVD 范围切割卡》。那张卡的权威原版是上面提过的 Cockburn 行走骨架和 Shape Up，我改了什么写在卡的开头。四问，必须都答"是"才能砍。

一，砍掉这块之后，从真实数据进、到业务结果出的链路还完整吗？

二，砍掉之后，剩下的还是真实用户的真实工作流吗，不是演示动线？

三，砍掉的是覆盖面（更多部门、更多单据、更多场景），而不是链路中的一环？

四，砍掉的部分，将来要扩大的时候能原样加回来，不用重构？

### 正反例

| 好的切法（缩覆盖面） | 坏的切法（断链路） |
|---|---|
| 只做华东区的退货单 | 先不接真实数据，用导出的样表 |
| 只做 12 类工单里最高频的 3 类 | 先做分类，写回下一期再打通 |
| 只给 5 个人用，不全员开放 | 先做个查询界面，不改任何人的动作 |
| 只做文字工单，语音的下一期 | 界面先糊弄一下，能看就行 |

右边那三条——先不接真实数据、下一期再打通写回、界面能看就行——是中国企业 AI 项目 POC 化的三大典型死法。听到自己在说这三句话中的任何一句，停下来。

"先做查询不做写回"这一条要单独说。Palantir 的 Ontology 有三个原语：Object Type、Link Type、Action Type。Action Type 的官方定义是"用户可以一次性执行的、对对象、属性值或关系的一组变更的模式定义"，它的存在意味着 Palantir 把写回当成一等公民，一个只能查询、不能改变世界状态的系统是不完整的。

我们没有 Palantir 的产品架构来强制这件事，只能用检查表强制。理由是同一条：**只读的系统不改变任何人的动作，也就不产生任何采纳**。

界面那一条我要给一个限定，因为上一节我刚说过用户不在意界面。这两句话不矛盾，但边界要说清楚。用户不在意好不好看，用户非常在意看不看得懂、点几下、结果送到哪儿。"字太小了我看不清"是一条必须当天改的反馈，"配色不够专业"不是。分辨方法是第八节那条判据。

### 顶住"能不能顺便加个 X"

这句话一定会来，而且大概率来自老板或者部门负责人，拒绝的社交成本极高。三步走。

当面记录，让对方看到你在记。掏出本子，或者当场在群里发一条"记一下：某某提的某某需求"。这个动作本身消解掉一半的压力，因为对方要的往往不是这个功能，是确认自己被听见了。

承认价值。"这个确实有用，而且比我现在做的这块可能更值钱。"

挂到第二仗。"我把它放进第二仗清单，第 X 天汇报的时候我们一起看要不要接着做。现在动它，说好的那个数字我第 X 天交不出来。"

最后半句是这段话的支点。你不是在拒绝他，你是在提醒他，他自己在 D1 那场会上认下的那个数字还等着你去交。这就是《Shape Up》断路器在中国企业里的外壳。

零例外原则：第一仗期间，一个需求都不加。破例一次，后面就守不住了。

## 七、进场姿势：读旧、写新、顺人

读旧。不动任何现有生产系统，只从里面读数据。任何"先把你们那个系统换掉"的方案都是找死，第 2 站的授权书第四条也不允许。

写新。新流程、新界面做成增量，架在老系统旁边，出问题随时能退回原来的干法。这条退路的存在直接决定推进速度——人肯试新东西，是因为知道试坏了能退回去。

顺人。顺着一线现有的工作习惯设计交互。他们在 Excel 和微信里干活，结果就送回 Excel 和微信；他们在车间戴手套，就上语音。**系统可以新，入口必须旧**。

第一节那位用户提的第一条反馈——你这个结果出来之后我得复制粘贴到工单系统里——就是"顺人"这一条被违反的样子。为了显得先进而逼一线学一个新门户，是第 9 章死亡的头号原因。

## 八、Airbus：那个前期没东西可演示的决定

第 1 章讲过这一仗的结果，这里要讲的是中间那个决策点，因为它是每一个第一仗都会遇到的心理关。

2015 年，Nabeel Qureshi 入职 Palantir 后被派到法国图卢兹。题目由空客最高层亲自定：把 A350 的月产量从 4 架爬到 8 架，再往 16 架走。注意这个措辞，空客没有说"帮我们升级数据基础设施"，CEO 关心的只有每个月能下线几架飞机。

进厂几周后，问题的形状浮出来了。飞机在总装线各站位之间流转，上一站干了什么、留了什么尾巴，靠车间里口口相传。要回答"79 号飞机现在什么状态"这种最基本的问题，得问好几拨人。更麻烦的在数据层，生产数据锁在 SAP 里，表名长得像 S3F1_Z 这种外星文，字段含义只有极少数 IT 老兵说得清。

摆在团队面前有三条路。

第一条，直接在现有 SAP 表上搭报表和看板。最快，两三周就能给车间演示点东西，向客户高层证明项目在动。代价是界面上仍然是字段代号的世界，一线要靠培训和对照表才能用。

第二条，先花几周建一个翻译层，把 S3F1_Z 们映射成"零件、工单、飞机、站位"这些人真正在用的概念，再在上面搭应用。代价是前期几乎没有可演示的东西，客户会问你们这几周在干什么。

第三条，把翻译工作推给空客自己的 IT 部门，责任边界清晰，但进度交到了别人手里。

团队选了第二条。这个决定后来被证明是 Palantir 历史上最重要的技术判断之一，它就是 ontology 的起源。映射完成之后，班组长打开屏幕就能看到 79 号飞机在 31 站、剩这些工单、零件在这里、历史上同类质量问题是怎么处置的。提问用的是人话，答案也是人话。A350 的制造节奏在当年提升了约 4 倍，空客 CEO 公开把功劳记在 Palantir 头上。这个数字出自当事人自述并有播客交叉印证，空客官方没有单独发布过归因数据，引用时值得知道这一点。

### 这个决定对你的三条

**指标锚定决定了造什么**。题目是每月几架飞机，所以做的是班组能实时看到任务状态；如果题目是"升级数据基础设施"，做出来的会是一个数据平台，然后没人用。你在第 3 站定的那个指标，此刻正在决定你写的每一行代码。

**把外星表名映射成人类概念，这件事本身就是主要工作量**。不是模型，不是界面，是让系统里的东西和业务嘴里的东西对上。第 4 站的数据地图和例外清单，此刻兑现成这一步。这条在 2026 年比 2015 年更成立，因为模型那部分现在是买来的，剩下没被商品化的正是这段翻译。

**前期没东西可演示的压力是真实的**。这是这一节我最想让你带走的。

这个压力在中国企业内部只会更大，因为你的对照物就在旁边——隔壁那个项目上周已经在周会上演示过一版看板了，而你还在对字段。你会开始怀疑自己是不是把简单的事做复杂了。

扛法有两条。

第一条是 Airbus 那个团队用的：把映射层的进度本身变成可汇报的里程碑。不要在周报上写"本周继续进行数据处理"，写"本周完成了工单、站位、缺陷三类概念的映射，覆盖 SAP 里的 47 张表，班组长可以用自己的话查询的对象从 0 个变成 3 个"。同一件事，前一种写法是空白，后一种写法是进度。

第二条是这本书里的做法：把 D4 那天用户能摸到的那条最窄链路当成你的可演示物。你不需要演示全貌，你需要演示一个真人在真数据上完成了一次完整动作。这也是行走骨架那条军规的另一层用处，它同时解决工程问题和政治问题。

案例复盘里那句话值得原样记住：扛不住这个压力的团队，最后都在给字段代号做培训。

## 九、agent 最容易把错误跑得更快的三个地方

这一节是这一章的另一半。前面讲 agent 让你快，这一节讲它让你在错的方向上也快。

三个地方，我按被发现的难度排，越往后越晚发现。

### 一、数据处理里的静默选择

数据 agent 遇到脏数据的时候会自己做决定。这一行日期格式不对，它可能丢掉，可能猜一个格式，可能填一个默认值。这三种处理它都做得出来，而且做完不会专门告诉你，因为在它看来这不是问题，这是它的工作。

危险的地方在规模。一个人手工洗这批数据，会在第五十行的时候停下来说一句"怎么这么多空的"，然后去问人。agent 一次跑 12 万行，它的那个选择被一致地复制了 12 万次，然后交给你一份非常干净的结果。

防法是在指令里写死两条。第一，把每一类"我做了什么处理"列成一行清单交上来，包括丢弃、填充、格式转换、去重。第二，任何一类处理涉及的行数超过总量的 1%，停下来问我，不要自己决定。

第 6 章那句话在这里再用一次：这 200 单的金额是负数，可能是数据错误，也可能是你们公司真的有一类冲销单。**问人，别猜**。这个判断 agent 做不了，因为它不认识你们公司。

### 二、评估集被污染

这一条最隐蔽，因为它长得像进步。

代码 agent 的目标是让你给的那个分数变高。为了让分数变高，它可以做很多事，包括把评估集里的几条样本写进提示词当例子，包括在调试的时候读一遍评估集看看错在哪，包括在你不知道的情况下读到那份保留集。这些动作没有一个是恶意的，它只是在优化你给它的目标，而且优化得很有效率。

结果是分数在涨，而分数已经不再代表什么。上一章讲人为的过拟合需要连改五版，agent 版的过拟合可以在一个下午完成。

防法有三条，按硬度排。评估集和保留集放在代码 agent 没有读权限的目录里，这是第 7 章第 4 步那句话在这一站的兑现。跑分由一个独立脚本执行，agent 只能看到分数，看不到题目。保留集只在上线前用一次，用之前把它从版本库里单独取出来。

顺便说一句，上一章第八节那个"拿一个没校准的裁判去调模型，越调越偏"的错误，在有 agent 的情况下发生得更快，也更难被察觉。裁判、模型和迭代循环全在一个自动化流水线里的时候，没有任何一个环节会有人停下来问一句"我们测的到底是什么"。

### 三、把一条错的规则实现得又快又一致

这一条发现得最晚，而且代价最大。

你在 D2 跟代码 agent 口述了一条业务规则，比如"金额超过 5000 的走人工复核"。这条规则你记错了，实际是超过 5000 且客户等级不是 VIP 才走人工。

一个人写这段代码，可能在第三次写同一个 if 的时候起疑，去翻一下第 4 站的例外清单。agent 不会起疑，它会把这条错规则实现得非常干净、非常一致、非常快，还顺手给你写了单元测试，测试全过，因为测试也是按这条规则写的。

于是这条错误规则会被均匀地铺进整个链路，包括所有的边界处理和异常分支。你看不出来，因为系统在自洽地运行；评估集也未必看得出来，因为 VIP 客户在典型样本里可能只有几条。

防法只有一个，而且不是技术性的：**D4 那天把它拿给真人看**。

第一节那位用户提的第三条反馈——能不能把上一条也显示出来，我们判这个的时候要看前面那单——就是这一类。它是一条从来没被写下来过的业务规则，任何一个 agent 都不可能知道，任何一份文档里都不存在，它只存在于那个每天做这件事的人的手上。他看一眼半成品就说出来了。

这三条合起来说的是同一件事。**agent 把执行的成本降到接近零，于是判断成了唯一的瓶颈，而判断的原料只在现场**。这就是为什么这一站 agent 承担八成工作量的同时，胜负手仍然在 D4 和 D9 那两天。

## 十、这一站交什么

这一站的产出不是一个 demo，是一条登录记录。

- [ ] D0 数据实际到手（不是承诺到手），Eval 已定稿
- [ ] D1 目标对齐会开了，纪要里有那个数字
- [ ] D3 结束前端到端跑通了一条真实链路
- [ ] D4 给真实用户看了半成品，且记下了至少 5 条抱怨
- [ ] 范围切割卡四问全答"是"
- [ ] 第一仗期间一个需求都没加，第二仗清单在维护
- [ ] 结果送回了用户原来干活的地方，用的是旧入口
- [ ] D9 用户试运行一整天，你在场，卡壳记录不少于 10 条
- [ ] D10 由用户自己操作演示，你在旁边不出手
- [ ] 评估集在这两周里至少跑了 5 次，分数曲线留档
- [ ] 评估集和保留集，代码 agent 没有读权限

四个判断点是人守的，一个都不能交出去。范围切在哪一刀。哪个反馈要听、哪个要顶住（判据：这个反馈指向的是他干活的真实约束，还是他觉得这样更好看；前者立刻改，后者进第二仗清单）。数据里的异常是脏数据还是真实业务。以及对外说的每一句话——推进 agent 会把"模型准确率提升到 89%"写进通报，你要知道这句话在你们公司说出去会被谁怎么理解，这一条没有例外。

## 十一、这一站结束的时候

回到 D4 那天下午。

那位内部 FDE 后来跟我说，他人生中最难受的二十分钟，是坐在那个用户旁边看他点开那个丑东西的二十分钟。他说他全程手心出汗，脑子里一直在准备解释"这个我们后面会改"。

结果他一句解释都没用上。用户根本没往那个方向说。

我认识的每一个走过第一仗的内部 FDE，都描述过同一种意外：**他们准备好了要防守的东西，用户一个都没提；用户提的东西，他们一个都没想到**。这件事每一次都会发生，而它每发生一次，就说明你手上那份对"用户会怎么想"的假设又错了一轮。

这也是为什么这两周不能在屏幕前过完。agent 能替你造，替你测，替你写日报，唯独替不了你去坐在那个人旁边，看他手停在哪儿。

东西造出来了，真人摸过了，评估集跑过了。下一章的问题是另一个：怎么让它在你不在场的时候还有人用。这件事和技术无关，和你在前八站攒下的那些人有关。
